## Product Vision

SCA is not only an authentication service. It is a permanent ownership and provenance platform for collectible eyewear.

Every qualifying physical pair should receive a permanent SCA record before sale:

- Authentication completed
- Condition graded
- Registry record created
- Unique SCA Certification ID
- Permanent QR identity generated by SCA
- Printed QR physically included with the eyewear

For Second Chance Eyewear purchases, Shopify records the sale and purchaser reference. SCA links the exact sold physical pair to that sale and marks the buyer eligible to claim. After receiving the eyewear, the customer scans the printed QR, signs into or creates an independent SCA account, and claims the already-authenticated pair for free. The pair then appears in **My Collection**.

A Shopify purchase is **claim eligibility**, not permanent registered ownership. Ownership is registered only through the SCA claim flow.

Future ownership transfers append to the provenance record rather than overwriting prior owners.

External eyewear not purchased from Second Chance Eyewear can later enter SCA through paid authentication.

## Final Shopify / QR Model

### Shopify
Commerce source for:

- Products / variants / SKUs
- Inventory state
- Orders / payment events
- Original purchaser reference

### SCA Platform
Canonical system for:

- Unique physical eyewear identity
- Certification ID
- Authentication record
- Condition grade
- Inspection images
- Permanent QR identity
- Claim state
- Current registered owner
- Ownership history
- Transfer history
- Service history
- Certification / registry status
- Lost / stolen status
- Collector collection
- Insurance / document outputs
- Future market-history features

The canonical QR is generated by **SCA, not Shopify**. The Shopify app may later show SCA status, Certification ID, record links, or View/Print QR actions to staff, but those are integration conveniences. Shopify must not become the provenance database.

A Shopify product or variant is not automatically the same as one physical SCA record. Every uniquely certified physical pair receives its own SCA item and QR.

## Interfaces

1. **SCA Admin / CRM** — physical item intake/mapping, authentication, grading, certificates, QR generation/printing, customers, ownership, transfers, service events, reports.
2. **Collector Portal** — account, claim ownership, My Collection, certificate, transfer ownership, service history, lost/stolen actions.
3. **Public Registry / Passport** — QR verification, authenticity, condition, public provenance/status without exposing private personal data.

## Hosting Principle

SCA is now authorized as a **greenfield build from scratch**.

The currently available blank VPS is a **temporary construction/staging environment**, not the permanent home of SCA. The implementation must be portable to a future permanent server without rebuilding the application, regenerating permanent QR codes, resetting customers, or rewriting provenance history.

The temporary VPS must never be the only place where irreplaceable source, database, media, or secrets exist.

## Delivery Rules

- One current implementation task only in `NEXT_TASK.md`.
- ChatGPT is the authority that writes or replaces the current implementation task after architecture review.
- Claude must not expand scope beyond that task.
- Claude must stop after returning task evidence and wait for ChatGPT audit before doing additional implementation work.
- Claude must not self-approve completion or invent the next task.
- Every completed task must return evidence and commit SHA(s).
- Architecture changes require an ADR before implementation.
- Secrets, Shopify client secrets, access tokens, database credentials, and production keys must never be committed.
- Historical provenance records are append-only at the business-logic level; owner/service/transfer history must not be silently overwritten.
- Permanent QR URLs must use a Jeremy-controlled domain and must never depend on the temporary VPS IP/hostname.

See `docs/EXECUTION_WORKFLOW.md` for the mandatory Architect → Claude → Audit → Next Task loop.
