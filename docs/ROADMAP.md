# SCA Implementation Roadmap

## Delivery Principle

Build the permanent provenance platform in controlled layers while reusing mature MIT-licensed CRM infrastructure where it reduces commodity development. The current VPS is temporary. Every phase must preserve portability to a future permanent server.

Delivery is controlled through three levels:

- `docs/ROADMAP.md` — phase-level destination and milestones;
- `TASK_QUEUE.md` — ordered implementation backlog and dependencies;
- `NEXT_TASK.md` — the single task Claude is authorized to execute now.

Claude must not execute directly from this roadmap or from the queue. ChatGPT audits each completed task and promotes exactly one next task into `NEXT_TASK.md`.

Every implementation task must preserve its findings and evidence in Git through logical commits plus a committed report at `docs/task-reports/<TASK_ID>.md` in the private implementation repository.

## Phase 0 — Architecture Freeze

**Goal:** lock the rules before product code.

Accepted decisions:

- greenfield implementation; do not recover the inaccessible old Ownership Bridge;
- current VPS is temporary construction/staging infrastructure;
- implementation source belongs in a separate private Git repository;
- Krayin CRM is the initial MIT-licensed staff admin/operations foundation;
- Laravel/PHP + MySQL/MariaDB replace the prior Next.js/PostgreSQL/Prisma requirement for the initial admin foundation;
- SCA-specific functionality is implemented in isolated Laravel/Krayin modules/domain code where practical;
- avoid invasive vendor-core edits;
- Shopify remains commerce source;
- SCA remains provenance/ownership source;
- QR identity is generated by SCA, not Shopify or generic CRM functionality;
- permanent QR uses a Jeremy-controlled domain, never a temporary IP/hostname;
- Shopify purchase = eligible to claim;
- SCA scan/login/claim = registered owner;
- ownership/service/transfer/status history is append-only at the business-logic level;
- collectors do not use the Krayin staff interface;
- migration to permanent infrastructure and Krayin upgradeability are design requirements from day one.

**Status:** ACCEPTED via ADR-0005 + ADR-0006, subject to implementation validation of the selected Krayin release.

- private SCA implementation repository;
- repeatable Krayin installation on temporary VPS;

- secure admin initialization with no default credentials retained;
- environment configuration with no secrets committed;
- health/smoke checks;

- SCA module/package extension path demonstrated without product-domain implementation;
- confirmation no vendor-core edit was required;

Exit proof:

- CRM starts and staff login works;

- no hard-coded temporary server identity;
- no committed secrets/default passwords;
- SCA extension mechanism works without modifying vendor core;
- selected version/license/dependencies are documented;
- known security/upgrade risks are committed and either resolved or explicitly queued.

## Phase 2 — SCA Domain Module and Provenance Schema

**Goal:** create the permanent SCA business model inside controlled SCA modules, not generic CRM entities.

Planned task sequence:

- `SCA-DOMAIN-DESIGN-003` — exact schema, invariants, state machines, and migration plan;
- `SCA-DOMAIN-CORE-004` — implement models/migrations/services/tests.

Core concepts:

- `collector_accounts`
- `eyewear_items`
- `authentications`
- `certifications`
- `ownership_events`
- `transfer_requests` / `transfer_events`
- `service_events`
- `status_events`
- `shopify_sale_links`
- `qr_identifiers`

Core state flow:

```text
UNCLAIMED
  -> SOLD_AWAITING_CLAIM
  -> REGISTERED
  -> TRANSFER_PENDING
  -> REGISTERED (new owner; old history retained)
```

Exit proof:

- SCA schema/migrations are isolated and version controlled;
- one physical pair exists independently of Shopify/Krayin generic product definitions;
- append-only provenance behavior is enforced/tested;
- duplicate active ownership/claim conditions are blocked;
- Krayin upgrades are not dependent on rewriting SCA business history.

## Phase 6 — Collector Accounts, Claim, and My Collection

**Goal:** provide a premium SCA customer experience separate from the staff CRM.

Planned task sequence:

- `SCA-COLLECTOR-AUTH-011` — independent SCA collector identity/authentication;
- `SCA-CLAIM-012` — scan/sign-in/claim ownership workflow;
- `SCA-MY-COLLECTION-013` — collector collection experience.

Flow:

1. customer receives physical eyewear and printed SCA QR;
2. scans QR;
3. sees authenticated record and Claim CTA when eligible;
4. signs in or creates SCA collector account;
5. SCA verifies claim eligibility;
6. ownership event is appended;
7. state becomes REGISTERED;
8. item appears in My Collection.

Collectors must not be exposed to Krayin's staff/admin interface.
